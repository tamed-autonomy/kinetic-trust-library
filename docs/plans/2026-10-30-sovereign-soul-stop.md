# Registered sovereign return path for an authenticated Soul veto

Hand-back proposal `5ea926338cb69a80fa9cf6a816334891acf9bed5` Section 4.3
requires Soul/sovereignty stops to preserve `ClosedByAuthority`. System/principal
stops use `Contest`; the two destinations are not interchangeable. The original
subject's recipient owes the hand-back/SLA; no acknowledgment SLA or demand for
an appeal is imposed on the community that refused.

`InstalledNativeSoulStopResolver` accepts only a current actual native `RB_GATE`
whose complete installed ordinary verifier authenticated a stage-8 `TP_VETO`.
It binds the actual operation and signed Soul claim, a current managed relation,
the active original grant and its original registered template. A private
installed literal authority-URI mapping names the actual registered sovereign
authority; candidates cannot choose or downgrade it. The named-authority template
adapter must select that exact `closed_by_authority` route before preparation.
Unknown/unregistered authority is not inferred or converted to system contest.

The genuine preparation Source owns actual sealed context, durable cause/stop
registration and delivery. Shared registered-stop validation rereads current
clearance and requires exact original wire, `Exceeded`, `exceeded_soul`, sovereign
origin, the same named authority and unchanged grant/intent/relation/admission.
It never grants execution, changes a community's refusal, sends onto that
community or claims delivery. Existing system/software/native stop paths retain
their original system recourse checks by default.

Real signed native integration checks the authenticated veto, unknown-authority
rejection before preparation, refusal of a substituted system contest route and
the final closed sovereign hand-back. Operational registries, genuine sealing,
delivery and interruption are modeled Source responsibilities rather than
observed deployment effects.
