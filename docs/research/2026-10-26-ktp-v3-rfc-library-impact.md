# KTP RFC v3 research: Library impact

**Observed 2026-10-26.** This note distinguishes the immutable RFC `v2.1.0` baseline, unpublished changes already on RFC `main`, and open v3 proposals. It is an impact inventory, not an implementation or conformance claim.

## Source state and release rule

- Kinetic Trust Library currently pins RFC `v2.1.0` at `15520035267546e1035aad7beea0cc3cf9ef8f2c`; its public contract matrix marks proof issuance/verification, Core evaluation, profile validation, Decision Record projection, and trajectory continuity as partial. [Library contracts](../traceability/library-contracts.md).
- RFC `main` was `6035a2fe929d5d0546961cd084a8b0719eb7ab79` when inspected. It contains considerable **unreleased** draft work beyond `v2.1.0`, including [operational readiness](https://github.com/nmcitra/ktp-rfc/blob/6035a2fe929d5d0546961cd084a8b0719eb7ab79/specifications/operational-readiness.md), [complete trajectory signatures](https://github.com/nmcitra/ktp-rfc/blob/6035a2fe929d5d0546961cd084a8b0719eb7ab79/specifications/trajectory-signatures.md), [human eligibility](https://github.com/nmcitra/ktp-rfc/blob/6035a2fe929d5d0546961cd084a8b0719eb7ab79/specifications/human-eligibility.md), and [privacy evidence](https://github.com/nmcitra/ktp-rfc/blob/6035a2fe929d5d0546961cd084a8b0719eb7ab79/specifications/privacy-evidence.md). The [unreleased changelog](https://github.com/nmcitra/ktp-rfc/blob/6035a2fe929d5d0546961cd084a8b0719eb7ab79/CHANGELOG.md) records these; presence on `main` does not make them part of the immutable v2.1.0 tag.
- [Release proposal #182](https://github.com/nmcitra/ktp-rfc/issues/182) governs the proposed v3.0.0 set, review floors, dependencies, vectors, and planned December 10 tag. It says the date is a plan and the tag waits for its criteria. No `release/v3.0.0` remote branch or v3 tag was present in the refreshed checkout. Many relevant PRs remain open and stacked on other proposal branches, so a PR head is not a standalone complete baseline.

## Broader v3 set and scope boundary

[Issue #182](https://github.com/nmcitra/ktp-rfc/issues/182) also lists nested zones [#159/#160](https://github.com/nmcitra/ktp-rfc/pull/160), federation [#173/#174](https://github.com/nmcitra/ktp-rfc/pull/174) and [#177/#178](https://github.com/nmcitra/ktp-rfc/pull/178), repair [#171/#172](https://github.com/nmcitra/ktp-rfc/pull/172), conformance claims [#163/#166](https://github.com/nmcitra/ktp-rfc/pull/166), and boundary/execution observation proposals [#189/#190](https://github.com/nmcitra/ktp-rfc/pull/190) and [#187/#188](https://github.com/nmcitra/ktp-rfc/pull/188). These can justify pure declarations, parsers or calculations when accepted. Zone operation, cross-zone transport, reconciliation workflow, action execution, attestation truth, persistence, and enforcement remain outside the Library's current [documented boundary](https://github.com/tamed-autonomy/kinetic-trust-library/blob/main/README.md).

Open [PR #200](https://github.com/nmcitra/ktp-rfc/pull/200) proposes retiring stale v1 native Transport definitions; it does not itself imply a new Library transport implementation. The already-on-`main` trajectory signature and readiness drafts deserve their own gap rows because current Library trajectory support is semantic parsing and adjacent-pair assessment, without authenticity or lifecycle operation. See the [Library matrix](../traceability/library-contracts.md) and RFC [unreleased migration notes](https://github.com/nmcitra/ktp-rfc/blob/6035a2fe929d5d0546961cd084a8b0719eb7ab79/MIGRATION.md).

## Planning consequences

1. Build a clause/schema/vector delta from the **final merged v3 tag**, keeping proposal snapshots in a separate review ledger. For early development, pin each candidate PR head and mark tests provisional.
2. Design a breaking native-v3 replacement around the coupled changes: five-factor inputs and demand supplier, subject/External Root shape, proof format and request binding, Decision Geometry, and component claim language. Historical signed v2 records keep their original interpretation in archives; the v3 Library does not need to accept them or offer a runtime fallback.
3. Sequence focused implementation and vectors after the RFC's [dependency order](https://github.com/nmcitra/ktp-rfc/issues/182): Core inputs and evidence; identity/standing; proof; request association; Decision Geometry; component claims. Review readiness, trajectory and broader zone/federation contracts against the final tag for pure Library ownership rather than assuming every RFC MUST becomes Library code.
4. Keep Library package version, `KTP_SPEC_TAG`, and `KTP_SPEC_COMMIT` at v2.1.0 until v3 adoption is reviewed. A 3.0.0 Library release requires a final immutable RFC pin, relevant official vector evidence, migration documentation, and coordinated Service compatibility.
