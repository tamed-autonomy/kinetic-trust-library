## 2026-10-28 source reconciliation

The pure External Root lifecycle projector now matches 22 published lifecycle boundary cases over authenticated events, including expiry at equality, unresolved lapse, non-renewability, cause precedence, future events and rejected-cause non-revival. It validates event subject/instrument binding and finding-to-claim links; contradictory findings or conflicting records with the same digest yield no credit (`unverifiable`). Inputs must already be authenticated and authorized by the installed root profile. It neither verifies signatures nor establishes exposure, accountability chains or the complete candidate set; those remain part of the native standing integration.

Installed demand classification now checks the assessment's operation, deployment and exact evaluation time, passes immutable operation bytes to the installed formula and retains the source assessment. Unavailable criticality is read as 1. The formula is evaluated at zero, actual and maximum criticality; each finite common-scale A must preserve the restrictive ordering for this invocation. Global monotonicity/calibration remains the installed profile's responsibility. `project_classified_native_core` consumes the sealed result without accepting a bare candidate A on that path. The original scalar Core projection remains an explicitly non-authorizing arithmetic diagnostic.

Native envelope projection enforces E=0 and A>E before division, the zero-margin veto at equality, installed supervision bands and at least assisted supervision for unknown capacity. Threshold decisions compare ratios by exact cross multiplication; the displayed margin is rounded independently. It supplies a supervision floor, not execution permission; envelope ceilings, readiness, grants, replay and proof acceptance still require composition.

An installed demand verifier now binds immutable JCS deployment, supplier and verification profiles by their exact digests. Only its locally installed adapter processes evidence; candidates cannot select a verifier. The adapter must authenticate the complete payload, supplier independence/source path, provenance admissibility and current revocation, returning canonical payload bytes and complete provenance bytes. Deterministic checks then establish time, unit, deployment and operation binding. Derived results retain original evidence and separate observed values from unavailable restrictive readings. All 42 published value cases run through an actual ES256 fixture adapter, including wrong key/purpose/signature and source/provenance failures. The unsafe fixture encoding is test-only; no universal production envelope is invented. Operational adapter errors propagate. This boundary does not classify final A or grant execution.

The demand provenance precheck now hashes complete supplied evidence bytes exactly, rather than reconstructing a JSON evidence object. The fixture's canonical JSON is only one possible evidence encoding. A focused non-JSON case accepts the matching bytes and rejects a one-byte change. The installed verifier must separately establish the supplied reference/source metadata and admissibility; digest equality alone supplies no authority.

RFC `main` is `9612f79`; no v3.0.0 tag exists. The listed PRs remain open. Their conformance files moved upstream to `specifications/conformance/` and schemas to `schemas/`; the local `spec/proposals/` paths are retained as development snapshots. PR #203 added a negative sensor-configuration case: `moment_criticality` cannot be a sensor factor. The local vector and sensor-config schema now match that head, and the new schema-boundary validator passes all six configuration cases. It checks only shape, not feed authenticity or independence.

The Trust Proof, request-binding, Decision Geometry, External Root, and demand-supplier vector hashes are unchanged at their refreshed heads. PR #195 clarifies Basic/Standard/Full cryptographic floors; this library's isolated signature check remains a base capability and must not be represented as level conformance. Main's #180 and #206 clarifications keep Soul outside weighted R and define one R input; the native five-factor path already follows those boundaries. PR #195 still references the v2 risk-factor schema, while PR #203 rewrites that same v2 `$id` to five factors on its separate branch. Do not resolve that cross-PR conflict by silently replacing the library's pinned v2 schema. Person-subject, additional v3 limits, and other open proposals require a separate accepted contract before they become native proof or Core behavior.

PR #202 now has a local-only deterministic demand precheck against its declaration and value schemas. It matches the proposal's pure time, deployment, operation, provenance digest, range, and unit boundaries, including the exact freshness limit. The published declaration schema references the deployment profile's `demand_input` definition; the Library resolves that definition from a bundled snapshot and does not fetch schemas over the network during evaluation. The precheck does not process signed bytes or establish supplier independence, source access, provenance admissibility, or clock authenticity. The fixture's wrong-signature case intentionally passes this pure precheck and remains rejected by the proposed complete verifier. See [release-readiness audit](../plans/2026-10-28-v3-release-readiness.md).

The native software-agent Core projection now composes the current 70/30 `E_base` allocation, declared peer share, minimum ceiling, five-factor R and `E_base × (1 − R)` using exact Decimal arithmetic. It requires a derived base-trust result before projecting risk and capacity; a Soul veto or unanswered query leaves all later result fields absent. A zero-credit External Root imposes the `external_root_missing: 70` cap even if an input ceiling list omits it. The DI10 worked example yields exact `R = 0.53975` and `E = 43.72375`; this remains a diagnostic path until the RFC resolves its displayed `0.54`/`43.7` precision. Neither the caller-provided standing evidence nor demand is authenticated by this projection, and its A/E relation is never an authorization result.

The refreshed full Library suite passed 821 tests on 2026-10-28 with the optional v3 dependencies present. The wheel build included the new v3 sensor schema and validator.

The fixtures are proposal snapshots under `spec/proposals/`, not released normative vectors. Refresh them with the exact approved RFC commit before any v3 release.

The provisional implementation and proposal checks ran with the proposed `v3-proofs` dependencies available: `PYTHONPATH=src:/private/tmp/ktp-v3-deps python3 -m unittest discover -s tests -q` passed 820 tests on 2026-10-26. The optional JCS/schema tests skip when that extra is absent. A local wheel build included the pinned schemas, and installed-wheel native v3 imports and digest known answers passed. This is Library test evidence for the pinned proposal snapshots, not an RFC or deployment conformance claim.

## Findings from implementing the vectors

1. **Friction at exactly 0.3 is a real migration boundary.** The current v2.1 Library accepted an `ELEVATED` PoR declaration at `0.3` and awarded zero credit. PR #193 classifies `0.3` as `CALM`. The provisional v3 path now classifies it as CALM and rejects a conflicting ELEVATED category. The Library still has no signed-record release provenance in `PoRAttestationDeclaration`, so it cannot grant the proposal's optional tagged-v2 grandfathered credit. Native v3 can require fresh PoR declarations at cutover; it need not admit historical v2 declarations. Keep archived signed bytes unchanged outside the v3 authorization path.
2. **The embedded sponsor reference cannot establish sponsorship.** The v2.1 standing code compares the sponsored identifier's third segment with the sponsor identifier's final segment. PR #194 explicitly makes that segment opaque and requires an authenticated Sponsorship Bond's full `sponsor_id` URI to bind subject, bond and proof. The new pure binding validator passes the proposal's cases, including an unrelated opaque reference. It assumes the bond and proof have already been authenticated, as the vector preconditions require. Replace the incompatible v2.1 `StandingDeclaration` inference with a v3 standing input carrying the verified bond; do not preserve the old inference as native-v3 behavior.
3. **Proposal vectors cover pure decisions, not runtime proof.** The friction vectors do not test attestation authenticity or historical admission. The identifier binding vectors assume an applicable authenticated bond and proof. Passing them does not demonstrate signature verification, replay control, authority, or deployment conformance.
4. **The five-factor worked example needs an explicit precision rule.** [PR #164's DI10 vector](https://github.com/nmcitra/ktp-rfc/blob/ae8b4a9b95e131d4e96a34db6f6ea4dd227d37dc/specifications/conformance/demand-input-v1.json) lists five input values and weights whose exact decimal sum is `R = 0.53975`. It expects `R = 0.54` and `E_trust = 43.7` for `E_base = 95`, consistent with rounding R to `0.540` before deflation. Applying Core's stated `E_trust = E_base × (1 − R)` to the exact sum yields `43.72375`. The provisional pure v3 calculator returns the exact sum, while its test shows the displayed `0.54` after two-decimal rounding. Before integrating it into authorization, the RFC should say whether intermediate R is rounded, at what precision and rounding mode, and whether the vector's displayed values are normative or illustrative. A boundary near `A = E_trust` could otherwise change the result.
5. **Unknownness survives the factor's restrictive reading.** [PR #203](https://github.com/nmcitra/ktp-rfc/pull/203) makes an unobservable factor's `decision_stress = 1` separate from a measured value. The provisional factor-boundary primitive enforces that split and preserves canonical three-field undefined-input records. Its tests cover the proposed factor-boundary projections, including backup continuity and unknown required signals. It consumes already established signal population and measured aggregate; it does not authenticate feeds, prove redundancy independence, derive signal population, or evaluate Soul. The current v2.1 `UndefinedInput` carries provenance and older reason labels; replace that public shape and evaluation path at the v3 cutover.
6. **Proof verification stages need a trusted boundary.** PR #195 has a single ordered verifier. The provisional stage-1 parser checks compact framing, bounds, strict UTF-8, duplicate-free JSON, safe numbers, depth 32 and exact RFC 8785 JCS. The stage-2 predicate checks the exact protected type, locally installed ES256/EdDSA choice, and closed header. The stage-3 predicate checks a locally supplied key record's revocation, role, issuer, zone, algorithm and curve metadata. The stage-4 predicate verifies original compact signing bytes using ES256 (including raw low-s signature rules) or Ed25519, given an already trusted key. The stage-5 predicate checks issuer, audience, safe-integer NumericDates, ten-second lifetime, trusted clock, and signing-key interval. The ordered internal precheck matches the first five stages across all 100 proposed cases. A separate stage-7 predicate matches the proposed subject/lineage/zone, ceilings, root expiry and ingress cases, failing closed when a required ingress verifier is absent. These pieces cannot accept a proof on their own: real trusted key lookup/current revocation, corrected stage-6 schema/extension handling, complete ingress verification and final gate processing still need a native v3 verifier. The caller-supplied algorithm tuple and key record are safe only when sourced from authenticated local configuration; this precheck must not be exposed as proof acceptance. The parser and signature primitive require the proposed `v3-proofs` optional dependency and fail closed if unavailable.
7. **Request association binds both complete sides.** PR #196's known answers confirm that the complete compact JWS, including both separators and the signature, is hashed with the `KTP/trust-proof-v3` domain prefix and selected SHA-256 or SHA-384. The provisional request primitive checks the closed proposal schema, JCS-encodes the complete supplied request, and hashes it with the separate `KTP/request-binding-v1` prefix. Both SHA-256 and SHA-384 known answers match. These pure primitives do not verify that the proof is accepted or that the request was reconstructed from an actual invocation. The hash algorithm must be selected by installed policy, not an untrusted digest prefix. Actual request construction, independent classifier/context matching, delegation, replay reservation and signed carriage remain unimplemented.
8. **PR #195's schema rejects its own clear vector.** The proposed v3 Trust Proof schema references the immutable v2 `risk-factors.json` `$id` for `ktp.context`. That v2 schema requires six members, including `moment_criticality`. PR #195's signed `clear` fixture and PR #164's five-factor rule omit `moment_criticality` from context, as intended for v3. Validation of the published `clear` fixture therefore fails at `ktp.context` before the claimed `TP_CLEAR` result; 22 declared `TP_SCHEMA` cases reject as expected, but every published clear case also rejects. The RFC needs a new v3 five-factor context schema (with a distinct `$id`) or an equivalent corrected inline definition, and refreshed vectors if the contract changes. The Library retains the exact proposed schema as a diagnostic and will not make stage 6 pass by modifying its local copy.
9. **Decision Geometry digest is ready as a primitive.** PR #197's two known answers match after closed schema validation, JCS of the complete body, and the `KTP/decision-geometry-v1` NUL-prefixed SHA-256/SHA-384 preimage. The validator resolves the request-binding and association references from pinned local schemas only. This does not establish that the input observations, gate order, supervision, tightened constraints, or signed carrier are valid; those require separate evaluation and authenticated context.
10. **Stage-7 invariants can be exercised despite the schema blocker.** A separate predicate matches PR #195's proposed subject/lineage/generation, zone, score/ceiling, External Root expiry and ingress-failure cases. It requires authenticated expected subject, zone, ceiling policy and ring depth. When a required ingress path exists, absence of a real verifier fails closed; the current Library does not verify nested-zone receipts. This predicate remains outside proof acceptance until the corrected schema and all ordered stages are assembled.
11. **External Root will change the proof wire contract.** [PR #201](https://github.com/nmcitra/ktp-rfc/pull/201) at `3e8f5d0a17bedfd7d4bb1b6430410340c3d8b2d7` proposes a closed `none`/`sponsorship_bond`/`external_attestation` root union and explicitly calls for regenerated canonical Trust Proof fixtures and dependent request-association/Decision Geometry digests. The pinned #195/#196/#197 fixtures are independently useful development targets, but they cannot simply be combined with #201's later root shape. The current stage-7 root check is only the #195 status/end-time subset. A separate pure selector matches #201's four strongest-single cases, given an already authenticated eligible candidate set with strength and complete signed-instrument digests; it neither validates candidates nor aggregates credit. Do not migrate the v2.1 property bag or issue a v3 proof until the merged root schema, source instruments and regenerated signed bytes are available.
12. **The major-version cutover should replace coupled v2.1 components.** The existing `core/evaluate.py` feeds the v2.1 six-factor `core/risk.py`; `models/proof.py` and `proofs/` encode the local `ktp+jwt` profile; `models/record.py` is a project-owned Decision Record. These are not native-v3 interfaces. The provisional v3 parser and signature checker currently import a few private v2.1 framing/algorithm helpers as implementation mechanics; audit and relocate any retained helpers before release so no v2.1 wire or policy assumption leaks into the new public path. Native 3.0 should replace the old public models and pipeline in the same distribution rather than expose a permanent dual-version API.
13. **Native five-factor risk now composes missing evidence without inventing a measurement.** `NativeRiskAssessment` takes exactly five sealed factor states and weights. Complete inputs yield exact measured and decision R; an unobservable factor contributes its restrictive decision stress to decision R while measured R remains absent and undefined inputs are preserved. It is a risk-stage result, not an authorization outcome. The PR #164 R/E precision question still blocks coupling this value to capacity decisions at a normative boundary.
14. **Demand operation binding is a separate preclassification digest.** PR #202's complete operation descriptor now matches both published JCS/preimage/digest known answers under its own `KTP/demand-operation-v1` domain. It excludes final A and `moment_criticality` to avoid a circular digest. This does not authenticate the supplier, value payload, independence, provenance, clock, or matching actual invocation. Those checks must precede consumption of a supplied demand-side criticality value; no requester scalar may replace them.
15. **The first native v3 Core path stops at Soul before risk.** A pure Soul query projection requires a declared nonempty applicable framework set, preserves absent/unanswered/stale/undefined query states, and lets a known veto remain a veto even when another query is unknown. `preflight_core` returns no risk value after veto or undetermined Soul; clear Soul advances only to the native five-factor risk assessment. These inputs still require independently authenticated framework responses and installed applicability. The preflight has no capacity, envelope or permission result.

## Next integration gate

Design a native v3 standing input that carries a validated Sponsorship Bond (or an immutable verified bond value). Then connect the pure identifier binding check to proof verification and standing preparation, using the accepted #149/#151/#157 contracts and their final vectors. Replace the incompatible v2.1 standing path; archive old signed records without offering them as native-v3 evidence.

For Core integration, resolve the precision question above and the separate [demand supplier proposal #202](https://github.com/nmcitra/ktp-rfc/pull/202): authentication, supplier independence, provenance truth and exact operation binding cannot be inferred from a caller-supplied scalar. The current v2 risk path still weights `moment_criticality` and must not be presented as v3 behavior.

For canonical Trust Proofs, resolve the upstream schema conflict, then extend the internal stage-1–5 precheck with the corrected closed schema, extension handling, invariants, ingress and gate result. The v2.1 proof parser has different wire bounds and must not be silently reused as a v3 verifier.
